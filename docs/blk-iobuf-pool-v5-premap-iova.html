blk-iobuf-pool-v5-premap-iova
NVMe commands past the 128 KiB dma_opt clamp, with no per-I/O IOVA allocation

A pool-backed io_uring fixed buffer, DMA-mapped once at registration and reused for every command, issues NVMe commands far larger than the 128 KiB dma_opt_mapping_size() clamp — proven at a single 8 MiB command — by allocating zero per-I/O IOVA. This is SPDK's map-once mechanism, inside the kernel driver, with IOMMU isolation retained.

base: linux.git v7.2-rc1 branch: blk-iobuf-pool-v5-premap-iova commits: 8 (over the pool substrate) mechanism: 8 MiB command proven perf eval: in flight (SPDK parity)

01What it does

On a translating-IOMMU host, nvme-pci folds dma_opt_mapping_size() — the IOVA rcache bound, 128 KiB — into max_hw_sectors (commit 3710e2b056cb), because a per-command DMA mapping allocates and frees an IOVA and large IOVA allocations were thought not to scale under iova_rbtree_lock. Every NVMe command on such a host is therefore capped at 128 KiB.

This branch escapes the cap the way SPDK does — by not allocating a per-I/O IOVA at all. A pool-backed buffer is DMA-mapped once at io_uring registration and reused for every command, so the clamp need not apply. nvme publishes a second limit, max_hw_premapped_sectors (= NVME_MAX_BYTES with the dma_opt clamp removed, MDTS folded in); premapped requests split at it, while ordinary I/O keeps the dma_opt-clamped max_hw_sectors. Unchanged, safe defaults; opt-in large commands.

02Mechanism (iova-native)

At registration the pool reserves one contiguous IOVA for the whole buffer with dma_iova_try_alloc() + dma_iova_link() per folio; struct blk_dma_premap holds it and is handed to a request via blk_iobuf_fixed_buf_premap(). The consumer is the nvme io_uring_cmd passthrough path (/dev/ngXnY); completion skips the unmap. Two design gates, both load-bearing:

  • Coherent-only (dev_is_dma_coherent()): a persistent reused mapping does no per-command cache maintenance, correct only on coherent DMA. A per-folio dma_sync_single on iova addresses trips DMA_API_DEBUG and is deliberately absent.
  • Needs a translating IOMMU: dma_iova_try_alloc() returns false otherwise and the buffer falls back to ordinary (nothing to beat).

05The performance question: does map-once still matter after the clamp is simply lifted?

David Lohr Bueso's dma-opt-clamp-report argues the clamp is obsolete: since the scatterlist-less DMA helpers (858299dc6160) and nvme-pci's conversion (7ce3c1dd78fc), a request takes a single IOVA allocation for the whole transfer, so larger requests reduce allocator work. His fix is far simpler than premap — lift max_hw_sectors to the true ceiling and opt in per-device with the existing max_sectors_kb sysfs knob. If that is all it takes, does premap's map-once buy anything?

the hypothesis David's lift removes the ceiling but keeps two per-I/O taxes premap removes: a per-command IOVA allocation (fast now, but not free) and a per-command page pinning (get_user_pages). At a matched large command size, those are amortized away by the smaller command count — so David wins the big-transfer case cleanly. The premap edge, if any, is at high IOPS / high core count, where command count stays high and the per-I/O tax caps kernel scaling below SPDK. Premap is the same map-once mechanism SPDK uses; the test is whether it closes the last CPU-per-GB / saturation-IOPS gap that per-I/O allocation leaves open. The two are complementary: lift the ceiling (David) and remove the per-command tax (premap).

The arms — a factorial that separates the two per-I/O taxes

Premap removes two different per-I/O costs, so the eval must separate them. get_user_pages (page pinning) is removed by any registered buffer — the pool, op-38 — not by premap specifically; the per-I/O IOVA allocation is removed only by map-once (premap / SPDK). The baseline that lifts the ceiling to the true device MDTS via the ordinary per-I/O path is David Lohr's patches — the upstream-representative control (our iova-512k rcache proxy was limited to 512 KiB; David's reaches the full MDTS, so B-vs-A is apples-to-apples at any size).

Each contrast isolates one variable: A2 → A3 the get_user_pages (pin-once) win on a lifted ceiling; A3 → B the per-I/O IOVA-allocation cost — what premap adds beyond the pool; B vs C premap-vs-SPDK parity. Sweep matched command sizes (128 KiB, 512 KiB, and up to the real MDTS on a large-MDTS drive), QD {1, 16, 64, 128}, cores {1, 4, 8, 12}, dedicated namespace. Measure IOPS & GB/s at saturation, host CPU% (mpstat) → CPU-per-GB, p99/p99.9, and confirmed on-wire size. Prediction: at large command size all converge on bandwidth (David's point); as cores rise at fixed size, A2/A3's CPU-per-GB climbs while B and C stay flat — and the load-bearing test is A3 → B: if B tracks C and separates from A3, map-once earns its place beyond the pool.

one kernel, all arms A1–B run on a single binary = blk-iobuf-pool-v5-premap-iova + David Lohr's two patches applied on top (his ceiling-lift keeps the default at 128 KiB, so it is opt-in and never disturbs A1). Arms are selected at runtime, no reboots and no kernel-version confound: A1 = default (max_sectors_kb=128); A2 = echo <MDTS> > max_sectors_kb (David's opt-in, ordinary path); A3 = A2 with an op-38 pool fixed buffer (removes get_user_pages); B = the premapped fixed buffer (additionally removes the per-I/O dma_map/IOVA). Only C (SPDK) is a separate user-space stack.
honest framing If arm B does not separate from arm A at high concurrency, then on modern kernels David's one-liner-scale change is sufficient and premap's added complexity (dma_iova plumbing, coherent-only gate, io_uring fixed-buffer path) is not justified for the command-size problem alone. The pool's separately-measured ~40% pin-once host-CPU saving is a different axis (get_user_pages) and stands regardless.

The 8 MiB reproduction uses an emulated MDTS (the kdevops iobuf-nvme-8m defconfig + QEMU MDTS-lift patches) — no physical drive here advertises an 8 MiB MDTS, so the multi-MiB single command remains a QEMU-emulated result until a large-MDTS device (physical or emulated) is run through the test above. The Latitude performance eval runs on bare metal, but its Micron MDTS (~512 KiB) bounds the premapped command there.
